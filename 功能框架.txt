0. 一句话定位
================================================================================

把安卓 TVBox 的「配置订阅 + 多站点聚合搜索 + 多线路选集播放」这套能力搬到
Windows 电脑上，界面走纯白极简路线，但利用电脑宽屏优势把内容密度做高：
一屏能看到足够多的海报、剧集和搜索结果，鼠标操作优先，键鼠快捷键齐备。


================================================================================
1. 技术选型
================================================================================

外壳        Electron                跨平台桌面外壳，Windows 免额外工具链
构建        electron-vite           主进程/预加载/渲染进程三端统一构建
界面        React 18 + TypeScript   组件化 + 类型安全
样式        原生 CSS + CSS 变量     不引入 UI 框架，纯白设计体系完全自控
状态        Zustand                 轻量全局状态（配置源、站点、播放状态）
路由        react-router-dom        HashRouter（桌面端避免 file:// 路由问题）
播放        ArtPlayer (MIT)         开源播放器内核，控制条可完全自定义
流媒体      hls.js (Apache-2.0)     m3u8 / HLS 播放，兼容绝大多数采集站
HTML解析    cheerio                 用于 type=1 的网页型站点兜底解析
编码        iconv-lite              GBK/GB2312 直播源与网页转码
本地存储    JSON 文件               放程序同级的 data\ 目录（便携），避免原生模块重编译
打包        electron-builder        NSIS 安装包 + 免安装 zip

设计原则
  1) 主进程负责一切网络请求与文件读写，渲染进程只管展示（安全 + 可绕过 CORS）
  2) 不引入需要 node-gyp 编译的原生依赖，保证 clone 下来就能跑
  3) 所有对外协议尽量兼容 TVBox 既有生态，能直接吃现成订阅

3. 核心概念与数据模型
================================================================================

3.1 ConfigSource  配置源
    一条订阅记录，指向一个 JSON 配置文件（远程 URL 或本地文件）。
    {
      id        : string    本地唯一 ID
      name      : string    显示名
      url       : string    远程地址 / 本地绝对路径
      kind      : "url" | "file"
      enabled   : boolean   是否参与聚合
      lastSync  : number    上次同步时间戳
      raw       : object    上次成功拉取的原始 JSON（离线可用）
      error     : string    最近一次同步失败原因
    }

3.2 Site  站点（影视源）
    一个可直接查询的资源站接口。
    {
      key         : string        唯一标识（csp_xxx）
      name        : string        显示名
      type        : 0|1|3|4       站点类型，见第 4 章
      api         : string        接口地址
      ext         : string        扩展参数（部分 spider 需要）
      jar         : string        依赖的 spider 标识
      searchable  : 0|1           是否支持搜索
      quickSearch : 0|1           是否参与快速搜索（首页搜索）
      filterable  : 0|1           是否支持分类筛选
      playerType  : number        播放器类型（1=普通，2=解析）
      categories  : string[]      站点自带分类名（P1）
      style       : {type,ratio}  列表卡片样式提示
      header      : object        站点专属请求头
      timeout     : number        超时秒数
      group       : string        分组（来自哪个配置源）
      enabled     : boolean       桌面端本地开关
      health      : number        最近一次连通性测试延迟(ms)，-1 表示失败
    }

3.3 Vod  影视条目（列表态）
    {
      vod_id, vod_name, vod_pic, vod_remarks, vod_year, vod_area,
      vod_actor, vod_director, type_name, vod_score,
      site_key, site_name, source_id          ← 桌面端附加：来自哪个站点/配置源
    }

3.4 VodDetail  影视详情（继承 Vod）
    {
      vod_content   : string      剧情简介（HTML，需清洗）
      vod_play_from : string      线路名，用 $$$ 分隔，如 "线路1$$$线路2"
      vod_play_url  : string      剧集，格式见 3.5
      lines         : Line[]      解析后的线路数组
    }

3.5 播放地址字段格式（TVBox 标准，必须兼容）
    单条线路内：  "第01集$http://a/1.m3u8#第02集$http://a/2.m3u8"
    多条线路线：  "线路1剧集串$$$线路2剧集串"
    分隔符：      $$$  分线路     #  分剧集     $  分「名称」与「地址」

3.6 Parse  解析接口
    { name, type, url, ext }
    type=1 为 JSON 解析接口： {url}{播放页地址} → {url: 真实地址, header: ...}

3.7 Live  直播
    LiveGroup  { name, channels: LiveChannel[] }
    LiveChannel{ name, url, group, logo, epg }

4. 自定义 JSON 配置格式规范   ★ 核心
================================================================================

桌面版同时支持「两种方言」，解析器自动识别，用户不用关心：

  A. TVBox 兼容方言   直接吃网上现成的订阅文件，零改动
  B. 简洁方言         字段更少、type 用可读字符串，适合自己手写

--------------------------------------------------------------------------------
4.3 站点 type 取值与桌面端支持策略
--------------------------------------------------------------------------------

  type  含义                        桌面端策略
  ---------------------------------------------------------------------------
   3    苹果CMS / MacCMS V10 接口    ✅ 完全支持（主力，生态里 90% 的源是这类）
   1    网页型 / JSON 规则型         ✅ 支持（用 rules 规则 + cheerio 解析）
   4    影视TV 系 CMS 变体           ⚠️ 按 type3 协议尝试，多数可直接用
   0    需配套 spider(jar) 的聚合     ⚠️ 无法执行 Java jar，标记「需 Spider」并跳过；
                                      若配置里给了 api 则降级按 type3 试
   2    自定义/其他                  ⚠️ 标记为不支持，仅展示

  说明：安卓版 TVBox 的 spider 是 dex/jar 字节码，桌面端无法直接运行。
       因此本项目的兼容重点放在 type=3（苹果CMS）与 type=1（网页规则）。
       这也是现有公开订阅里覆盖度最高的两类。


--------------------------------------------------------------------------------
4.4 苹果CMS(type=3) 接口协议（桌面端实现依据）
--------------------------------------------------------------------------------

  分类列表   {api}?ac=list&t={分类id}&pg={页码}
  分类详情   {api}?ac=detail&t={分类id}&pg={页码}
  影片详情   {api}?ac=detail&ids={影片id}
  关键词搜索 {api}?wd={关键词}&ac=detail
  分页搜索   {api}?wd={关键词}&ac=detail&pg={页码}

  统一返回：
  {
    "code": 1, "msg": "数据列表", "page": 1, "pagecount": 100,
    "limit": "20", "total": 2000,
    "list": [
      {
        "vod_id": 123, "vod_name": "片名", "vod_pic": "https://...",
        "vod_remarks": "更新至20集", "vod_year": "2024", "type_name": "电视剧",
        "vod_play_from": "线路1$$$线路2",
        "vod_play_url": "第1集$http://...#第2集$http://...$$$第1集$http://..."
      }
    ]
  }

  容错要求：
    - code 可能为 1/"1"/"ok"，统一归一化
    - type_name 可能为 "电视剧,国产剧"，取第一个
    - 部分站点返回 vod_play_from 与 vod_play_url 数量不一致，以短的为准
    - 部分站点搜索接口需 ac=detail&wd=，部分只认 ac=detail&ids=，做自动重试


--------------------------------------------------------------------------------
4.5 桌面端扩展字段（写在任意配置里都生效，安卓端会忽略，不破坏兼容）
--------------------------------------------------------------------------------

  "tvboxDesktop": {
    "minVersion": "0.1.0",
    "theme":   { "accent": "#2563EB", "posterRatio": 0.66, "density": "compact" },
    "siteOverrides": [
      { "key": "csp_ExampleCms", "timeout": 30, "searchable": 1,
        "header": { "Referer": "https://example.com/" } }
    ],
    "externalPlayer": { "command": "", "args": ["{url}"], "prefer": ["PotPlayer","mpv"] },
    "home": { "sections": [ { "title": "近期热门", "site": "csp_ExampleCms", "typeId": 1 } ] }
  }

  设计意图：扩展只做「覆盖」不做「新增语义」，任何一份扩展过的配置丢给安卓 TVBox
  仍然可用（多余字段被忽略），反过来安卓的配置拿来也能直接跑。


--------------------------------------------------------------------------------
4.6 配置来源与导入方式
--------------------------------------------------------------------------------

  1) 远程订阅 URL   —— 输入地址，一键拉取，支持一键更新
  2) 本地 JSON 文件 —— 文件选择 / 直接把 .json 拖进窗口
  3) 多源合并       —— 多个配置源同时启用，站点按 key 去重，后面的源不覆盖前面
  4) 单站点临时粘贴 —— 设置页可直接粘贴一段站点 JSON 快速试

5. 功能模块清单
================================================================================

【P0 · 核心链路，第一版必须可用】

  M01 配置源管理
      - 添加/编辑/删除/启用禁用订阅，远程 URL 与本地文件皆可
      - 一键同步、显示站点数量与上次同步时间、失败原因
      - 原始配置本地缓存，断网也能用上次的数据
      - 配置导入 / 导出（含单个配置源的分享文本）

  M02 站点管理
      - 站点列表：名称 / 类型 / 分组 / 来源配置 / 启用开关
      - 搜索、按类型与分组筛选、批量启用禁用
      - 连通性测试（发一次 ac=list，显示延迟或失败原因）
      - 站点排序（决定搜索结果展示顺序）

  M03 聚合搜索
      - 输入即搜（300ms 防抖），并发上限可配（默认 8），单站点超时 10s
      - 结果按「影视条目」聚合：同一部片子不同站点归到一张卡，卡上标注可用站点数
      - 顶部站点筛选 chips，可只看某个站
      - 搜索过程中流式返回（哪个站先回就先显示，不用等全部完成）

  M04 详情页
      - 海报 / 片名 / 年份 / 地区 / 演员 / 导演 / 分类 / 评分 / 简介
      - 多线路切换 tabs（线路1、线路2…）
      - 选集网格，支持「正序 / 倒序」切换，支持剧集搜索定位
      - 从搜索结果进入时保留返回位置

  M05 播放器
      - ArtPlayer + hls.js，支持 m3u8 / mp4
      - 自定义白色控制条：播放暂停 / 进度 / 音量 / 倍速(0.5-3.0) / 画质 / 截图 / 画中画 / 网页全屏 / 全屏
      - 键盘快捷键：空格播放暂停、←→ 快退快进 10s、↑↓ 音量、F 全屏、
        N 下一集、P 上一集、Esc 退出播放
      - 自动连播下一集、跳过片头片尾（可配）、记忆播放进度
      - 播放失败自动尝试下一线路 / 下一个解析

  M06 直播
      - 解析 m3u / txt 两种格式，支持 #genre# 分组语法
      - 左侧分组列表 + 右侧频道列表，点击即播
      - GBK 编码自动识别转码

  M07 收藏与历史
      - 收藏影视，本地持久化
      - 观看历史：最近观看、看到第几集、播放进度，支持断点续看
      - 首页「继续观看」横向滚动条

  M08 自定义 JSON
      - 完整支持第 4 章两种方言
      - 可视化 JSON 编辑器（带语法校验与错误定位）
      - 导入 / 导出 / 复制分享文本


【P1 · 体验增强】

  M09 解析接口（parse）
      - 网页型播放地址调用解析接口换取真实地址
      - 解析失败自动轮询其他解析接口，记录可用性排行
  M10 外部播放器
      - 自动探测 PotPlayer / mpv / VLC 安装路径
      - 一键用外部播放器打开当前剧集，可配置启动参数模板
  M11 首页内容位
      - 「继续观看」「最近更新」「分类推荐」若干横向内容条
      - 数据来源为配置里 tvboxDesktop.home.sections 指定的站点分类
  M12 界面设置
      - 强调色、海报比例、内容密度（舒适/紧凑）、深色模式（可选）
      - 窗口尺寸记忆

【P2 · 后期】

  M13 下载（m3u8 合并，依赖 ffmpeg，需检测环境）
  M14 弹幕（第三方弹幕库对接）
  M15 投屏 DLNA
  M16 豆瓣等榜单推荐位

================================================================================
7. 关键流程
================================================================================

7.1 启动流程
    读本地配置缓存 → 若超过 N 小时则后台静默同步 → 渲染首页
    （首屏不等待网络，先出缓存，网络回来再补）

7.2 聚合搜索流程
    输入关键词（顶部的全局搜索框）
      → 取所有 enabled && searchable 的站点
      → 并发池(8) 逐个发起：{api}?wd={kw}&ac=detail
      → 每个站点返回后立刻归一化并推送到渲染进程（流式）
      → 全部结束后做同名合并（见 7.2.1）：合成一张卡，卡上记录
        [{site_key, vod_id, vod_name, vod_remarks}] 列表
      → 用户点卡片 → 用信息量最高的那个站点进详情，详情页可切站点

7.2.0 分类浏览（用户要求「变成目录例如电影动漫一类的」）
    左侧导航第二项，页面本身没有搜索框 —— 找片名走顶部全局搜索框，
    这一页是「不知道看什么」时用的目录。同一个 Search.tsx 按 URL 上有无
    ?wd= 分成两种模式：有就是聚合搜索，没有就是分类浏览。

    打开时对每个 type 3/4 的启用站点请求一次 {api}?ac=list，
    从返回的 class 数组拿分类树，接着：
      · 按名字归并成统一大类：电影 / 电视剧 / 动漫 / 综艺 / 纪录片 /
        短剧 / 体育 / 少儿（顺序固定）
      · **归并要对着整条祖先链做，不能只看顶层**。真实站点会把类型混着挂：
        「记录片」挂在「电影片」下面（而且写的是「记录」不是「纪录」，
        漏这个字它就会留在电影里）、「短剧」挂在「连续剧」下面。只看顶层
        的话这些全都会进错桶。
      · **「动画片」归哪儿要看父分类**：挂在「动漫片」下面归动漫，挂在
        「电影片」下面则是动画电影，要跟着父分类归到 电影 → 动画 ——
        光速 / 素博 的同类内容叫「动漫电影」且本来就在电影里，不这么处理
        同一类内容会裂成两个区（这是用户报的「只显示几个子分类」的
        其中一面）。例外精确列在 LEAF_FOLLOWS_PARENT 里，只对祖先链
        匹配，别的站点真把「动画片」挂在「动漫片」下时不受影响。
      · **分类名命中 SKIP 就整棵子树丢掉**。SKIP 仍然是
        解说 / 演员 / 明星 / 资讯 / 新闻 / 预告 / 花絮 / 伦理 / 福利 /
        写真 / 片花 / 榜单，但**判定沿祖先链生效**：非凡 / 量子 / 天堂 的
        「伦理片」是电影片的**子分类**（光速 / 素博 才是顶层），只挡顶层
        名字的话这三个站的伦理片会漏进电影里 —— 这是实际出现过的 bug。
        过滤只按分类名，不做片名关键词兜底，而且只在分类浏览里生效，
        聚合搜索不受影响。
      · **大类下面再分子分类**（用户要求「有一部分影视完全分错区重新分」
        → 答复「把分区扩大」）。子分类归一表 SUBS 把各站的叫法收进
        统一名字：电影 → 动作 / 喜剧 / 爱情 / 科幻 / 恐怖 / 剧情 / 战争 /
        动画，电视剧 → 国产 / 香港 / 台湾 / 韩国 / 日本 / 欧美 / 泰国 /
        海外，动漫 → 国产 / 日本 / 欧美 / 港台 / 海外 / 动画电影，
        综艺 → 大陆 / 港台 / 日韩 / 欧美，体育 → 足球 / 篮球 / 网球 /
        台球 / 其他，短剧 → 擦边短剧 / 古装仙侠 / 现代都市 / 穿越年代 /
        言情总裁 / 重生民国 / 反转爽剧 / 脑洞悬疑 / 短剧。
        归一表里没有的叶子就直接用叶子自己的名字（实际站点里出现过
        「AI漫剧」这种表外叶子，会原样成为一个子分类）。
      · **父分类必须展开成叶子**：实测父分类 id 查不出任何东西
        （t=1 返回 0 条），leafIds() 递归取到最底层的 id
      · **分类树缓存两头都要能作废**。主进程 classCache 按站点 key 存、
        TTL 10 分钟（同一批请求会去重）；渲染进程还有一份 categories。
        换整套订阅时 key 变了能自然失效，但**原地改源地址 / 禁用某个站点**
        时 key 没变，两边都还认旧目录 —— 用户报的「子分类有 bug 只显示
        几个子分类」根因就在渲染进程那份：Search.tsx 里「categories 非空
        就不再拉」的守卫把旧数据锁死了。现在站点集合一变就走 staleCatalog()
        清掉渲染进程的 categories 与 browse，主进程侧也在 add / update /
        remove / sync / syncAll 五个 IPC 里主动 clearCategoryCache()。

    选中一个大类（或它的某个子分类）后，向每个站点发
    {api}?ac=detail&t=<叶子id>&pg=N，ac 用 detail 是为了顺带把
    vod_play_url 拿回来，进详情页不用再请求一次。

    **重复的 t 参数是「最后一个生效」而不是 OR** —— 这条是关键，
    早先按「服务端 OR」设计过，实测是错的：
      t=6（动作片）        total 4558，返回动作片
      t=7（喜剧片）        total 7176，返回喜剧片
      t=6&t=7              total 7176，返回**全是喜剧片** ← 只有最后一个生效
      t=6&t=7&t=8          total 2121，返回爱情片
      t=6,7（逗号）        total 4558，只认第一个
    所以「全部」是**每个叶子各发一次请求**（用 cursor + worker 并发池，
    并发数取设置里的 concurrency），拿回来用 interleave() 按子分类
    **交替穿插**合并（不是首尾相接，否则第一屏全是同一类型），
    再按 vod_id 去重、截断到 limit。模板式站点只有一个 {t} 槽位，
    只取第一个叶子。

    因为「全部」代价高（电影有 8 个叶子 × 5 个站点 = 40 个请求，
    实测 4–8 秒），点进多子分类的大类时**默认落在第一个子分类**上，
    想全看再点「全部」。

    页数优先读接口自己报的 pagecount：采集站每页固定 20 条，和请求里的
    limit 不一致，按「本页满没满」猜会永远算出 1 页。
    站点内取最浅子分类的 pagecount，跨站点取最大值。

    **向下滚动自动加载**（用户要求「每次往下翻电影的时候整成自动加载」）：
    底部放一个哨兵 div，用 IntersectionObserver（rootMargin 提前 500px）
    把「是否进入视口」记成一个布尔 state，再由一个 effect 判断要不要真发请求。
    不直接在回调里发请求，是因为「加载完新一页后哨兵可能还在视口里」这种
    情况不会产生新的交叉事件，光靠回调会卡住不再继续加载。
    两个坑：
      · effect 的依赖必须和哨兵 div 的渲染条件完全一致（含 !browse.running）。
        否则首屏还在请求、div 尚未挂载时 effect 就跑了一次、拿到空 ref 直接
        返回；等 running 变 false、div 真的出现时依赖没变、effect 不再重跑，
        观察器永远没挂上 —— 表现为滚到底什么都不发生。
      · 失败时页码不前进，必须靠 error 标记停下来，否则哨兵一直在视口里
        会无限重试同一页，把站点打爆。界面上显示原因 + 「重试」按钮。
    新一页接在已有结果后面（不是替换），并用 site_key + vod_id 去重 ——
    有些站点翻页是假的，会整批返回同一页。

7.2.1 同名合并规则（用户要求「把每个源的重复资源合成一个」）
    分组 key = normalizeName(vod_name)：
      全角转半角 → 去掉尾部别名括号 → 去噪声词（高清/超清/全集/国语版…）
      → 去标点与空格 → 转小写
    季数、部数、副标题保留，保证「第一季 / 第二季 / 之帝王业」不会被合成一部。
    尾部括号里若含「第N季/部/集/篇、特别篇、番外、前传、后传」则不去掉。
    每组内先按站点收敛：同一站点只留一条，排序依据是
    「有海报(+4) > 有备注(+2) > 有评分(+1)，同分取名字短的」。
    代表条目（显示用的片名与海报）取收敛后信息量最高的那条，
    其余条作为该卡的其它片源。
    排序：与关键词的匹配度（完全相等 < 前缀 < 包含 < 其它）→ 片源数多优先
    → 信息量 → 中文片名排序。

7.2.2 解说过滤（用户要求「去除掉每个源的电影解说」）
    两条线索任一命中即判定为二创内容：
      · 片名 —— 解说 / 速看 / 盘点 / 混剪 / 拆解 / 影评 / 剧情介绍 /
        一口气看完 / 分钟看完
      · 分类 —— vod_class 或 type_name 里含上述词（多数站点标「影视解说」）
    只按片名判断会漏掉片名干净、靠分类标记的条目，所以要两条都看。
    网页规则站拿不到分类字段（searchHtml 写死 type_name: ''），只能按片名判断。
    默认隐藏并计数，搜索页副标题写明「已挡掉 N 条解说」，
    搜索页与设置页都能关掉。不做时长判断——列表接口通常不返回时长。

7.3 详情流程
    选中 (site_key, vod_id) → {api}?ac=detail&ids={id}
      → 解析 lines：vod_play_from.split('$$$') 与 vod_play_url.split('$$$') 对齐
      → 每条线路内 split('#') 得剧集，每集 split('$') 得 [名称, 地址]
      → 默认选中第一条「首集地址看起来是直链」的线路的第一集
        （采集站常把网页分享页放在第 1 条线路，盲选会黑屏）
      → 详情页「选择片源」区块列出这部片子在其它站点上的条目，点一下换源

7.4 播放流程
    得到剧集地址 url
      → 若已是 http(s) 且以 .m3u8/.mp4 结尾            → 直接播
      → 若为网页地址且站点 playerType=2 / 配置了 parses  → 调解析接口
            GET {parse.url}{encodeURIComponent(url)}  → {url, header}
            失败则轮询下一个解析接口（最多 3 个）
      → 仍失败 → 提示「改用外部播放器打开」
      → 播放器就绪后写入历史（进度每 10s 落盘）
      → ended 事件 → 自动下一集

    播放页侧栏「片源」区块：列出这部片子在各个站点的条目，点一下换源继续看。
      换源链接只带 /0/0，进入后由播放页自动跳到该源里「能直接播」的那条线路；
      没走过搜索就直接打开播放页时列表为空，提供「找其它片源」按片名现搜一次。

    播放器下方的地址整块可点，点了用系统默认浏览器打开该地址；
    旁边另有「复制地址」按钮走剪贴板。

    注意：Artplayer 的 option 校验器要求 type 必须是字符串，
    显式传 type: undefined 会抛「'option.type' require 'string' type」并把
    整棵 React 树卸载。所以非 m3u8 时不要传 type/customType，让它按扩展名自己推断。

7.5 网络与反爬
    - 所有请求走主进程，默认带浏览器 UA
    - 站点级 header、全局 headers 规则（按 host 通配匹配）依次应用
    - 超时默认 20s，失败重试 1 次（指数退避）
    - 图片走渲染进程直连，失败降级为占位图

7.6 电视直播流程

    配置源里的 lives 字段（type 0 = txt，1 = m3u）→ 并发拉全部直播源
      → 按内容嗅探格式（出现 #EXTM3U / #EXTINF 就当 m3u，否则当 txt）
      → txt：`#genre#` 行开一个分组，其余行按「名称,地址」拆；
             地址右侧不像 URL 时再按 `#` 切一次
        m3u：#EXTINF 的属性段在最后一个逗号之前，显示名在逗号之后；
             取 tvg-name / group-title / tvg-logo
      → 按频道名精确合并成一卡多线路（同一地址去重）
      → 分组按频道数降序，`其它` 永远排最后

    主进程侧有一份 10 分钟缓存（换配置源时由 index.ts 主动作废）。
    渲染进程侧刻意**不**再缓存一份：早先写成「内存里有就直接返回」，
    结果同步完新订阅再进电视直播，看到的还是上一个源的分组，只有重启才好。
    现在每次进页面都问一次主进程，它缓存还新鲜时就是一个来回的 IPC。
    同一个源的失败提示只会弹一次，否则每次进页面都重复弹。

    **作废缓存光 clear 是不够的**：很可能正好有一次 loadLive 还在飞，
    它跑完会把上一个源的结果写回 cache，于是「换完订阅还是旧分组」又出现。
    这类竞态只在换源和首次加载撞上时才复现，表现成「自检第一次跑必挂、
    第二次才过」。现在用一个 generation 代次号：loadLive 开头记下当时的
    代次，写回缓存前比一次，换过源就不写（本次结果照旧返回给调用方）。
    category.ts 的 classCache / inflight 是同一个坑、同一套修法。

    点频道后播放器会自动滚回视野。频道多的时候（「地方频道」一个分组就有
    247 个）点列表靠下的频道，播放器早就滚出屏幕了，不拉回来就只看得到声音。
    用 scrollIntoView({block:'nearest'})，播放器本来就在视野里时不做任何滚动。
    trigger 用一个自增计数而不是 picked 本身 —— 重复点同一个频道时 picked
    的引用没变，拿它当依赖 effect 不会重跑。


7.6.1 房间号频道（huya:// 与 douyin://）

    虎牙、抖音这类平台的直播地址带防盗链签名、几小时就失效，写进直播源里
    第二天就是死链。所以直播源里只写房间号：

        游戏赛事,#genre#
        danking直播,huya://10188

    `huya://10188` = 虎牙房间 10188；`douyin://<web_rid>` = 抖音直播间。
    只有用户点开这个频道时才走一次 IPC 去平台换真地址，换好了才构造播放器。
    地址格式判定放在 shared/liveUrl.ts（主进程和渲染进程都要认），主进程那边
    的解析在 services/streamResolve.ts。

    另有一路「内置自定义频道」直播源（live.ts 的 BUILTIN_LIVE），
    即使没配任何订阅，游戏赛事分组里也一定有 danking直播。
    live.ts 的地址识别正则因此要从 https?/rtmp/rtsp/rtp/udp/file
    扩到带 huya/douyin，否则 `huya://10188` 会被当成分隔符串切坏。

    分组名归一：源里的 `•游戏「赛事」`、`•影视「轮播」`、`•咪咕「移动」`
    这类带装饰符的名字，先 stripDecorator 去掉开头的 •·・*-— 与「」【】《》[]（），
    再查 GROUP_ALIAS 别名表映射成 `游戏赛事` / `影视轮播` / `咪咕移动`。


7.6.2 三个必须记住的坑

    (1) 虎牙 TX / AL 两条线给的是「主播放列表」（只有 #EXT-X-STREAM-INF），
        里面那条变体地址被改写成
        `http://<边缘节点IP>/tx.hls.huya.com/src/…` —— 浏览器带着
        `Host: <IP>` 去拉**一律 403**。还原主机名、补 Origin、补 Referer
        全试过，还是 403。而 HS 那条直接给「媒体播放列表」（有 #EXTINF），
        分片是相对路径，实测 200 + video/MP2T。
        所以解析器要逐个探测，优先挑含 #EXTINF 的真媒体列表，主列表只当兜底，
        AL 排最后。判据不能只看「有没有 #EXTM3U」，否则会选到播不了的主列表。

    (2) `Referer` 是浏览器的 forbidden header。
        `xhr.setRequestHeader('Referer', …)` 会被**静默忽略** ——
        hls.js 实际发出去的是页面自己的来源（开发时 http://localhost:5173/），
        CDN 因此对分片回 403，而播放器**不报任何错**：readyState 停在 0、
        video.error 恒为 null，只表现为黑屏，极难查。
        修法只能在会话层补：主进程用
        session.defaultSession.webRequest.onBeforeSendHeaders
        给匹配的请求写上头。匹配要按**域名后缀**而不是 host，因为虎牙把
        真实主机名塞进了 path（`http://<IP>/tx.hls.huya.com/src/…`）。
        https 才补 Origin（http 下实测不需要，多补反而可能被拒）。

    (3) 抖音的取流接口不要签名：先进 https://live.douyin.com/ 拿 ttwid，
        再调 webcast/room/web/enter/（aid=6383、web_rid=<rid>，
        带 cookie 与 referer）取 hls_pull_url_map，status 2 = 直播中、
        4 = 本场已结束。但它的**分区 / 用户列表接口全返 444 Access Denied**
        （要 a_bogus 签名），首页和用户主页又是客户端渲染、没有 SSR 的
        web_rid —— 所以**没法自动发现某人的抖音直播间号**，只能由用户提供。


7.7 系统代理：一个长得像「播放器坏了」的环境问题

    界面里的海报和视频走 Chromium，主进程的请求走 Node，而两者对系统代理的
    处理**不一样**：Chromium 听 Windows 的代理设置，Node 的 fetch 不读它。
    所以当 Windows 的系统代理开着、指向的代理软件却没在跑时（Clash 内核退了、
    ProxyEnable 还留在 1），会出现：

      · 搜索 / 详情 / 分类 / 直播分组全部正常 —— 它们走主进程；
      · 但界面里**所有**图片和视频都黑，控制台一片
        net::ERR_PROXY_CONNECTION_FAILED。

    实测过一次：系统代理 127.0.0.1:7897、端口无人监听；渲染进程每个请求都
    ERR_PROXY_CONNECTION_FAILED，而主进程直连 img.dytt-tupian.com /
    vip.dytt-cinema.com/…/index.m3u8 / api.ffzyapi.com 全是 200、600–720ms。

    services/proxy.ts 在建窗口之前跑一次：resolveProxy 问出系统代理链
    （形如 "PROXY 127.0.0.1:7897"），对里面每个 host:port 做 800ms 的 TCP
    探测，**只要有一个在监听就照旧走系统代理**，一个都连不上才
    session.defaultSession.setProxy({ mode: 'direct' }) 并打一条 [proxy] 警告。

    注意每次启动只判断一次：启动时代理是死的、之后又把代理打开了，
    要重启应用才会用上。反过来，代理一直活着时这条逻辑完全不起作用。

7.8 AI 剧情总结（用户要求「在看视频链接的下面加一个 ai 总结」）

    位置：播放页视频地址下面。**点了才会请求** —— 进来一集就自动调一次既白花钱、
    用户也可能根本不想看，所以不做后台预取。

    链路：components/AiSummary.tsx（交互）→ IPC ai:summary / ai:summary-visual
    → services/ai.ts（发请求）。API Key 存在 data/settings.json 的
    settings.ai.apiKey，**只在主进程里用**，渲染进程拿不到，也不会随请求外传。

    两条路，界面上是两个按钮：

    （一）看一遍再总结（默认动作，用户原话是「让deepseek直接看一遍当前剧集
    而不是推测」）。渲染进程先用 utils/frames.ts 从正在播的 <video> 上按每 20 秒
    抽一帧（45 分钟一集约 130 帧，上限 MAX_FRAMES=120，宽 512、jpeg 质量 0.7），
    每帧前面拼一个 [mm:ss] 文字块，再作为 image_url 数组发给 deepseek-flash。
    它有多模态能力，所以写的是画面里实际发生的事。

      · **为什么 canvas 抓帧不会跨域**：ArtPlayer 用 hls.js 播 m3u8，<video>.src
        是 MSE 喂的 blob:，属同源，drawImage 之后 toDataURL() 不会抛
        SecurityError。直接给 <video src="http://别的域/x.m3u8"> 才会被拦。
      · 抽帧时会 video.pause()、逐个 seek、等 requestVideoFrameCallback
        （没有就退化成两层 rAF）再抓，结束还原原播放位置与播放/暂停状态。
        单个时间点 seek 超时就跳过它继续，不因为一帧毁掉整次扫描。
      · 进度通过 .ai-bar 展示「正在抽帧 N / M · mm:ss · x%」，带「停止」按钮
        （cancel 对象传进 captureFrames，每帧检查一次）。
      · 实测一集 70 帧：抽帧约 60 秒，请求 4 秒左右，15466 tokens，
        约两分钱。**只能用 deepseek-flash** —— deepseek-v4-pro 不收图。
      · detail:'low' 会让服务端先缩到 512×512；这些图本来就只有 512 宽，
        所以不亏。

    （二）只看资料：不抽帧，直接把 buildUser() 的文字发给模型，让它依据自己的
    剧集知识写。快、便宜，但对新剧和冷门剧基本是瞎猜。抽帧失败时不要点这个
    就能跳过看片。

    发给 DeepSeek 的内容全部来自站点已有字段，由 buildUser() 拼：
    片名 / 类型 / 年份 / 地区 / 导演 / 演员 / 评分 / 备注 / 站点简介（截前 1200 字）
    + 「当前正在看：第05集（第 5 集 / 共 212 集，线路「dyttm3u8」）」。
    看片模式另外还会带上抽出来的 JPEG 画面（data:image/jpeg;base64,...）。
    **播放地址不发。**

    模型与计费（2026 年现状）：deepseek-chat / deepseek-reasoner 已停用，
    现在用 deepseek-flash（默认）或 deepseek-v4-pro。思考模式默认开着且 effort=high，
    这里在请求体里传 {"thinking":{"type":"disabled"}} 关掉 —— 剧情总结不需要推理链，
    关掉更快更便宜。只看资料那条路实测一次 2260ms / 557 tokens
    （prompt 357 + completion 210），约 0.0012 元；看片那条路贵在画面，
    70 帧 15466 tokens。

    SYSTEM 提示词分两套。SYSTEM_TEXT（只看资料）：第一段 2–4 句讲这一集讲什么，
    然后「本集看点」下用「- 」列 3–5 条；**资料不足就如实说明，绝对不要编造
    具体的人物、台词或事件**；不要客套话、不要复述资料、400 字以内。
    SYSTEM_VISUAL（看片）：第一段 3–6 句按时间顺序讲剧情，然后「剧情节点」下用
    「- [时间] 内容」列 4–8 条（要求把相邻画面合并，不要一帧一条），再「本集看点」
    列 2–4 条；并写明**这些画面是每 20 秒抽一帧、而且没有声音** —— 画面上出现
    字幕或文字时可以照实引用，但不要编造对白、人物姓名或画面上看不到的情节；
    画面若全是片头/黑屏/静态图就直说信息量少，不要硬编；600 字以内。

      · 看片模式效果（实测《斗破苍穹年番》第05集，dyttzy，70 帧）：模型读出了
        画面上的硬字幕并照实引用（「这薛崩可是九星斗师」「萧炎哥哥终于出现了」
        「这股战劲就算是内院的佼佼者」「没想到云岚宗竟然还有一个云山活着」
        「父亲并未落入云岚宗」「我知道你并非萧家之人」），并按时间点给出 8 条
        「剧情节点」，还注意到开头三分钟是片头与版权页。**短板是没有声音**：
        带硬字幕的片读得准，不带字幕的只能描述画面在演什么、听不懂对白。
      · 站点接口不提供分集剧情，只看资料那条路只能拿全剧简介 + 集号推 ——
        提示词里那句「不要编」实测生效：模型会自己写「仅凭现有资料无法确定
        本集的具体情节」。
      · AiSummary 组件在 Player.tsx 里挂的 key 带集号
        （`${siteKey}/${vodId}/${lineIndex}/${epIndex}`），换集直接重建组件，
        上一集的总结不会留在屏幕上。
      · 没配 Key 时按钮禁用，并在下面给出「去设置 → AI 总结」的入口；
        主进程在**发请求之前**就抛「还没有配置 DeepSeek API Key」，
        所以绝不会偷偷联网。
      · explainStatus() 把 401 / 402 / 404 / 413 / 429 / 5xx 翻成人话，
        例如「DeepSeek 说这个 API Key 不对（401）。去「设置 → AI 总结」里检查一下。」
        413 单独提示「这次传的画面太多了，接口拒收」，对应抽帧间隔调大。
      · 主进程 ai:summary-visual 里 frames 为空会自动退回文本那条路，
        所以抽帧一个都没成时不会给用户一个空请求。

    设置页的「AI 总结」区块：API Key（type=password + 显示/隐藏）、模型
    （datalist 给 deepseek-flash / deepseek-v4-pro）、接口地址（留空 = 官方
    https://api.deepseek.com，也兼容任何 OpenAI 兼容服务，自动拼 /chat/completions）。
    **看片模式必须用支持视觉的模型（deepseek-flash）；选了 deepseek-v4-pro
    再点「看一遍再总结」，服务端会直接拒图。**

7.9 分类浏览翻页卡顿与详情页空白（用户报「每次一加载下一页会全部刷新且加载
    下一页速度太慢可以预加载点开片源再正式加载」）

  用户这一句话里其实是三件事：翻页时**前面已上屏的卡片被重排**、翻页**太慢**、
  以及**点卡片进详情页要先等**。问清楚两处含义后分别做：

  (1) 「预加载」= 首屏画完后**提前把下一页拉好**。
  (2) 「点开片源再正式加载」= 点卡片进**详情页**时，先把已经拿得到的信息
      （片名、海报、评分、备注）显示出来，线路与剧集慢慢加载。

  ── 为什么会「全部刷新」 ──
  不是分页坏了。实测每站 page1 与 page2 的 vod_id 集合重叠为 0（dyttzy / ffzy /
  guangsu / lzi / subo 全部是 0），page1 与 page3 也是 0 —— 每页内容确实是新的。
  真正的原因是 mergeResults() 的排序：第一关键字是「这条有几个源」
  （allSiteKeys.length），翻页追加的新条目里如果有和前面同名的，会并进已有的组、
  把那个组的源数抬高，那一组就整块跳到最前面。
  DOM 实测：加载第 2 页前 37 张卡，开头是 法医秦明之龙番往事 / 黑岛监狱 / 兰香如故；
  加载后 45 张卡，开头变成 惩罚者2026 / 蜂鸟行动 / 热血部落 —— 一次全变。

  修法：mergeResults() 多收一个可选参数 previousOrder?: Map<string, number>
  （归一化片名 → 上一轮的名次）。照原样排完序之后做一次「稳定分区」：
  名次表里有的进 known、按原名次排回去；没有的进 fresh、接在后面。
  搜索那条路不传这个参数 —— 那边本来就希望好结果往上浮。
  Search.tsx 用一个 useRef 维护名次表，只在 isBrowsing && browse.page > 1
  且分类没变时传出。
  · 这里踩了一个坑：名次表一开始写成「渲染中按 key 重置 + effect 里只追加」，
    结果**同一个分类再点一次时 orderKey 没变**，名次表沿用上一轮跑到第 20 页
    留下的名次（实测日志 seq 一直是 982，名次数组从 [0,-1,0,0,982] 变成
    [1,-1,45,100,982]）。必须 browse.page <= 1 就**整个重建**，而不是只追加。

  ── 预取 ──
  在 useApp.ts 里做模块级的一格预取位：
    let browsePrefetch: { key: string; promise: Promise<CategoryPage> } | null
    prefetchKey(bucket, sub, page)  →  `${bucket}::${sub}::${page}`
    startBrowsePrefetch(bucket, sub, page, pageCount)  到底 / 同一 key 在飞就跳过
    takeBrowsePrefetch(bucket, sub, page)              取走并清空
  browseCategory 成功后预取第 page+1 页；browseMore 先 takeBrowsePrefetch，
  拿到就直接用、拿不到才 window.api.category.browse()；clearBrowse 里置 null。
  预取的 promise 挂 .catch(() => undefined) 吞掉拒绝 —— **预取失败不弹提示**，
  真滚到那儿时 browseMore 会自然重试一次。
  实测：翻页耗时从冷拉的约 3.8 秒变成 **307ms**（首屏仍然约 2.7s，那是站点本身慢）。
  一个有意思的副作用：自检里原来那条「滚到底后又发了第 2 页请求」失败了 ——
  因为预取在滚动之前就发过了。这本身就证明预取在工作，于是把断言换成
  「卡片确实变多了」+「开头几张卡的位置没变」。

  ── 详情页先显示已有信息 ──
  Detail.tsx 原来 loading && !detail 时只渲染一个转圈，而且只从 search.results
  里找已知信息（从分类页进来的卡片数据在 browse.results，所以既没有已知信息、
  也看不到「还有 N 个片源」）。现在：
  · 新增 crossResults：searchResults 里有这个 siteKey 就用它，否则用 browseResults。
    preview 与 findSourceGroup 都改用它。
  · preview 的查找优先级：crossResults 里同 siteKey 且 vod_id 相同的那条 →
    favorites 里匹配的 → history[].items[] 里匹配的。
  · 加载态改成完整骨架页：.detail-head + .detail-hero（Poster）+ .detail-title +
    .detail-meta + .detail-pending（转圈 +「正在获取线路与剧集…」）+
    24 个 .sk-ep 骨架。
  实测冷卡片 #/detail/lzi/152870：+40ms 已经有真片名「逃出绝命街」、真海报、
  .detail-pending 与 24 个骨架集数；+320ms 换成真内容（1 集、1 条线路）。
  修之前 +60ms 是空标题 + 骨架。
  测这个时间线要注意：探针必须**先 location.hash='#/' 再 Page.reload**，
  否则重载会恢复上一次的 #/detail/... 路由、把详情提前缓存好，
  测出来的「瞬间就绪」是假的。

7.10 解析接口（M4-1，用户要求「开始m4」）

链路：播放页 → IPC parse:resolve → services/parse.ts → { ok, url, direct, parseName, ms, attempts, error }
      设置页「解析接口」区块 → IPC parse:list / parse:test / parse:add / parse:remove / parse:reset-stats

7.10.1 为什么需要它

采集站的线路经常给的不是直链，而是一个分享页地址。素博的 vod 42877 有两条线路：
  subyun    https://play.xluuss.com/play/nelOoxJd            ← 分享页，直接丢给播放器只会黑屏
  subm3u8   https://play.xluuss.com/play/nelOoxJd/index.m3u8 ← 直链
有 subm3u8 这种线路时，详情页的 pickPlayableLine() 会替用户挑中它。但**大量站点只有
分享页那一条线路**，这时候除了报错就只能交给外部播放器 —— M4-1 就是为了堵这个洞。

7.10.2 三步走，顺序很重要

resolvePlayUrl(rawUrl, { flag, prefer }) 按这个顺序试，任何一步成功就返回：

  第 1 步  本来就是直链？MEDIA_RE = /\.(m3u8|mp4|flv|mkv|ts|mov|avi|webm|m4v|mpd|mp3|m4a)(\?|#|$)/i
           命中就原样返回，direct=true，attempts 为空 —— 不白跑一趟网络。
           **刻意不做域名白名单**：采集站的 CDN 域名天天换，白名单只会误伤，
           宁可让一个伪装成 .mp4 的网页地址多走一次解析。
  第 2 步  先自己读一遍那个页面（tryDirect，label「直接从播放页里取」，strict=true）。
           十有八九是个 DPlayer 壳，地址明文写在脚本里：
             const vid = 'https://play.xluuss.com/play/nelOoxJd/index.m3u8';
           实测素博分享页 1205–2421ms 就能换出来，完全不需要解析接口。
  第 3 步  读不出来才按排行依次问解析接口（tryParse）。
           每个接口最多跟 MAX_HOPS = 3 次跳转，PER_PARSE 超时 8 秒，
           整体预算 PARSE_BUDGET = 24 秒。

7.10.3 排行怎么算（orderParses）

**分档比分数重要**。先分三档：
  档 1  解析接口 ext.flag 精确命中这条线路的 flag
  档 2  接口没声明 flag（通配）
  档 3  接口声明了别的线路
同一档内：type ≠ 0 的优先，再按 scoreOf() 排。scoreOf 用拉普拉斯平滑
  (ok + 1) / (ok + fail + 2) × 2 + 速度分
所以一个「成功 1 次」的接口会压过「失败 1 次」的接口，但压不过「成功 50 次」的。
战绩落盘在 data\parse-stats.json，设置页可以「清空排行」。

7.10.4 从网页里怎么把地址抠出来（extractUrl）

按顺序试，每一条都比上一条更宽松：
  a. 整个 body 就是一个地址
  b. parseLooseJson + deepFindUrl：递归找 url / playurl / play_url / m3u8 / src / video /
     link / address，以及 data / result / info / content 这些容器，深度 ≤ 4
  c. scanMediaUrl：**整段扫 m3u8，其次 mp4/flv/mkv/mov/webm/m4v/mpd** ——
     这条比猜变量名管用得多
  d. 8 条具名正则：var main= / var url= / "url":"…" / <video src> / <source src> /
     (?:src|url)= / player_aaaa 内嵌 JSON
     具名正则用 matchAll **遍历所有匹配**，不能只看第一个 —— 第一个往往是图片或脚本
另外 extractRedirect(body, base) 认 <meta http-equiv=refresh content="N;url=…">（两种
属性顺序都认）与 location.href= / location.replace( / location=，用 new URL(raw, base)
解析相对地址。

**踩过的两个真误报**（都在真实站点上撞到的）：
  · 腾讯剧集页扫出 https://vfiles.gtimg.cn/vupload/202005/07_common_avatar.png
  · 某个跳板页扫出 https://cdn.sm.cn/…/wasm_exec.js，还被当成「解析成功」
修法三件套：
  · requireMedia 严格模式（tryDirect 用）
  · NON_MEDIA_RE = /\.(js|mjs|cjs|css|json|xml|html?|png|jpe?g|gif|webp|svg|ico|woff2?|ttf|eot|map|txt|apk|zip)(\?|#|$)/i
    但**没有后缀的地址要放行** —— 很多直链就是不带后缀的
  · 拒绝返回「等于当前请求地址」的 URL（found === api 视为没找到）

7.10.5 公开解析接口的现状（决定了「不内置」这个选择）

用户拍板：**不内置任何第三方公开解析接口**，只认「配置里带的 + 设置页手动加的」。
这不是偷懒，是实测结论：
  · jx.aidouer.net  只回一个 meta refresh 跳到 jx.77flv.cc
  · jx.77flv.cc     2706 字节，加载 wasm_exec.js 与 77fv.js，**真地址由 JS 现算**
  · jx.xmflv.com    回「江湖路远，后会无期」停运页
  · okjx.cc / jx.jsonplayer.com / www.administratorw.com   直接 fetch failed
  · jx.parwix.com:4433                                      超时
也就是说 type=0 的浏览器嗅探早晚要做。M4 这一期只做 HTTP 解析（type=1/2）。

7.10.6 设置页那一块

标题「解析接口」，副标题报「N 条（配置里 X · 手动 Y）」。门头文案先把顺序讲清楚：
「应用会**先自己去读一遍那个页面**，读不出来才按下面的排行依次问解析接口。」
每行：名称 + 「配置里带的」/「手动添加」tag + type=0 警示 tag + 地址 + 「只解析 X / Y」或

7.11 首页内容位（M4-2，用户拍板「优先读配置的 tvboxDesktop.home.sections，没配就给默认」）

7.11.1 数据从哪来

  配置里带了 tvboxDesktop.home.sections  →  就按它来（origin='config'）
  配置里没写 / 一条都没配              →  每个可用 CMS 源给一条
                                            「<源名> · 最近更新」（origin='default'）

  为什么是 tvboxDesktop 这个命名空间：config.ts 里 ext = raw.tvboxDesktop，
  读的是 `home: (raw.home ?? ext.home)`。扩展字段统一挂在 tvboxDesktop 下
  对安卓 TVBox 无副作用（安卓只认 TVBox 自己的键），也避免和别人的 home 撞名。
  顶层直接写 home 也认，但订阅里推荐用命名空间那种写法。

  HomeConfig.sections[] 的形状是 { title, site, typeId? }。site 既可以是站点 key，
  也可以是站点中文名 —— matchSite() 四级匹配：key 精确 → 中文名精确 → 两边小写
  相等 → 互相 includes。用户手写配置时很难记得住 key，所以多给了后面三级。

  typeId 写了就是「分类推荐」，走分类浏览的地址
  （buildCmsBrowseUrl(site,'detail',[typeId],1)）；没写就是该源的「最近更新」
  （buildCmsUrl(site, { ac:'detail', pg:1 })）。

7.11.2 内置订阅里带了 5 条，开箱就有「最近更新 + 分类推荐」

  presets.ts 的 PUBLIC_CMS.config 和 samples/public-sources.json 里都写了同一份
  tvboxDesktop.home.sections，五行都是**在真实源上逐条验证过 20 条有内容**的：

    电影 · 最近更新     dyttzy            （最近更新）
    电影 · 动作片       ffzy    typeId 6  （分类推荐）
    电视剧 · 国产剧     lzi     typeId 13 （分类推荐）
    动漫 · 日本         guangsu typeId 42 （分类推荐）
    综艺 · 最近更新     subo              （最近更新）

  typeId 用的是苹果CMS v10 的默认分类 id，这几家采集站基本一致。五行混着
  「最近更新」和「分类推荐」是有意的：只用默认行为会得到五条一模一样的
  「最近更新」，只用分类又看不出「这个源现在更新到哪了」。

7.11.3 三条设计决定，以及为什么

  1. 一行失败不拖累别的行。loadSection() **不抛异常**，而是返回
     { ...base, items: [], error }。界面上那一行只显示一行错误文字，别的行照画。
  2. 缓存 10 分钟，但**失败的那几条只缓存 1 分钟**（ERROR_TTL）。实测素博第一次拉
     会抖一次 `fetch failed`，紧接着重试就好 —— 按 10 分钟缓存会让用户盯着
     一行错误看很久。有 error 的批次整体按 1 分钟算。
  3. 渲染进程不自己缓存，每次都问主进程。缓存键是「配置源的签名」，换源/同步立刻作废
     （clearHomeCache() 挂在 main/index.ts 里那 5 处 clearCategoryCache() 后面）。
     hero 上有个「刷新内容位」按钮走 force=true 强制重拉。

  matchSite 找不到站点时推一条 error 为「配置里写的影视源「X」不在当前已启用的源里」
  的 section；找到了但不是 CMS 类型（type 不是 3/4、或者被禁用/不支持）时推
  「X 不是苹果CMS 类型…」。去重键是 `${site.key}::${typeId ?? 'latest'}`。

7.12 外部播放器检测界面（M4-3）

7.12.1 检测范围扩大

  · 扫描清单加长：PotPlayer / mpv（含 mpv.net）/ VLC / MPC-HC（含 K-Lite 里的那份）/
    MPC-BE / KMPlayer / SMPlayer。

    `D:\某处\` 这种自定义目录里的播放器，扫路径永远扫不到，但用户多半把它设成了

7.13 电视直播线路体检（用户反馈：「电视直播线路太少很多都不能观看优化一下且画质过低」）

7.13.1 先量了一遍，结论是「不是源少，是死链多」

    16 个分组 / 627 个频道 / 831 条线路 / total 835
    多线路频道只有 108 / 627（83% 的频道只有一条线路，所以「线路太少」）
    IPv4（txt）705 条唯一地址 → 死链 191 条（27.1%）
    Gather.m3u  123 条 → 死链 108 条（87.8%，多为 neterr / 404）
    624 个频道里 202 个（32%）一条能播的都没有
    画质：master 播放列表 86 条里只有 6 条是多档；档位中位 1.3M、最高 6.256M；

  所以「画质过低」是能修的 —— 只要起播就挑最高档。

7.13.2 候选公开源全试过：加源没用

  · zbds-iptv4.m3u 是现有 IPv4 txt 的**严格子集**：两边完全相同 542 条，m3u 独有 0 条。
  · iptv-org/iptv/streams/cn.m3u   抽样 23% 可播
  · fanmingming/live/index.m3u     抽样 **0%** 可播（逐条打出来是 404/403，那批
                                   GD_CUCC/CCTV 已经撤了）
  · fanmingming/live/ipv6.m3u      7%
  · Kimentanm/aptv                 7%
  · Gather.m3u                     13%

  所以路线定为「把现有线路用起来」，而不是继续堆源。

7.13.3 用户的四个决定（都是推荐项）

  · 体检方式：点开频道时懒体检那几条 + 进分组后后台预热
  · 死频道：默认隐藏，顶部给「显示 N 个不可用」开关
  · 内置源：去掉 Gather.m3u，只留 IPv4 那条
  · 画质：起播就取最高档，之后允许 ABR 自适应降档

7.13.4 主进程 data 层的 `liveHealth.ts`

  常量：STORE='live-health'、MAX_BYTES=4096、OK_TTL=30 分钟、FAIL_TTL=5 分钟、
        DEFAULT_TIMEOUT=6s、MAX_CONCURRENCY=8、MAX_URLS=60。

  · **只读 4KB 就断开**（AbortController + reader.cancel()）：直播流是无限长的，
    绝不能拉完；判定「能拉起来」只要看响应头 + 头几 KB 里有没有 #EXTM3U。
  · 顺带从 m3u8 里正则取 `BANDWIDTH=` 与 `RESOLUTION=\d+x(\d+)` 记下**最高一档**，
    存进 LiveHealth { ok, ms, at, height?, bandwidth?, error? }。
  · 失败原因分开写：「HTTP 404」/「超时（6s）」/「不是 m3u8（text/html）」，
    不写笼统的「失败」—— 自检正是靠这个区分 404 与超时。
  · **体检请求带上配置里的请求头**（照 sites.ts 的 resolveHeader：所有启用配置源的
    headers → matchHeaderRules 通配 → settings.userAgent）。不少直播网关校验
    Referer/UA，不带的话会把好线路一律误判成 403。
  · 成功缓存 30 分钟、**失败只缓存 5 分钟**：上游偶尔抖一下，不该被记很久。
  · isProbeable(url) 只认 http(s)：huya:// / douyin:// 是房间号，探不了也不该算坏的。

7.13.5 渲染进程 Live.tsx

  · 进页面 health() 拉一次磁盘上的体检表；切分组后 400ms 预热当前分组前 60 条

  · 点频道：先找「可探 且 health.ok」的线路，有就直接用它；没有才先体检再挑。

    第 N / M 条」。latestRef 用 effect 同步（声明在播放器 effect 之前），

  · 死频道判定：ok === 0 && unknown === 0（所有可探线路都探过且全挂、又没有房间号

7.13.6 hls.js 画质

  核过 hls.js 源码（dist/hls.js:29110-29122）：startLevel = -1 时如果 levels > 1，
  它会 startLevel = 0 + bitrateTest = true —— **反而先从最低档做带宽测试**。
  所以正确做法是在 MANIFEST_PARSED 里算最高档（height * 1e6 + bitrate）并设
  `hls.nextLevel = best`：**不能用 currentLevel**，那会把 ABR 钉死；nextLevel 只影响
  下一片，之后 ABR 还能自己降回来。同时 abrEwmaDefaultEstimate 提到 4 Mbps，
  免得一上来从 500 kbps 估起。
  另外 ERROR 处理改成**先自愈两次**（NETWORK_ERROR → startLoad()，
  MEDIA_ERROR → recoverMediaError()），救不回来才提示。

8. 本地存储
================================================================================

位置：程序同级的 data\ 目录（便携形态，不写 C 盘用户目录）

  开发时      D:\tvbox\data\
  打包后      <exe 所在目录>\data\
  浏览器缓存  data\session\（Chromium 的 Cache / Local Storage 等都在这层）
  兜底        如果这个位置建不出来（例如装到了只读目录），自动退回系统默认的
              %APPDATA%\tvbox-desktop\，并在控制台打印一行提示，保证程序还能起。

  目录里存的文件：

  settings.json    应用设置（主题、并发数、外部播放器、窗口尺寸）
  sources.json     配置源列表 + 每个源最近一次成功的原始 JSON
  sites.json       站点本地覆盖（启用状态、排序、header 覆盖、健康度）
  favorites.json   收藏
  history.json     观看历史（vod_id、集数、进度秒、更新时间）
  live.json        直播源缓存

写入策略：内存态 + 200ms 防抖落盘，避免频繁 IO。
所有文件都是人类可读 JSON，便于用户手动备份与迁移。
第一次切到便携目录时，会自动把 %APPDATA%\tvbox-desktop\ 里已有的
settings/sources/sites.json 拷过来，升级不会丢配置。

用户报「在收藏与历史中加入播放进度条现在有bug」，以及随后的
「把不同资源同一部剧的观看历史合并」：

  进度条的 bug 不在进度条本身，在写入端。播放页**挂载的瞬间**就先
  save(true) 一次（这样一进片历史里就有了），可那一刻 video.duration 还是
  NaN，写进去的是 position 0 / duration 0；而 recordHistory() 又是无条件覆盖
  （按 `${siteKey}::${vodId}` 删旧行再 unshift）。于是在播放页按 Ctrl+R、
  或者应用恢复到播放路由时，挂载那一条会把已看进度抹成 0/0。
  实测 before 565/1387 → location.reload() → after 0/0；单纯切到 /library
  不触发（所以一开始误判成 teardown 事件的问题）。

  修法：recordHistory() 加合并规则 —— **同一集时，只有这次真的拿到了时长
  （duration > 0）才允许改写 position / duration，否则沿用上一次记下的值**。
  用「同一集」当条件是关键：换到别的集时 0/0 是诚实的，照常覆盖。

  界面侧顺带把条做显眼：原来是一条满宽 420px、3px 高的灰底条，1% 的填充
  看着就是一条分隔线。现在缩成 132px 的圆角胶囊、6px 高，右侧加
  「看到 9:23 / 23:07」（tabular-nums 防数字跳动）。首页继续观看卡也加了
  同样的细条。formatClock() 从 utils/frames.ts 挪到 utils/format.ts，
  和新增的 watchPercent() 一起给两处共用。

  **历史合并**：分组发生在**读取时**，history.json 里仍然是「一个源一条」，
  这样删掉某个源、或者换订阅，都不会把别的源的进度一起弄丢。

  - 归一键 normalizeName(name)：NFKC（全角转半角）→ toLowerCase →
    去掉所有空白与标点（/[\s\p{P}\p{S}]/gu）。
  - **刻意保守**：不剥「第二季」「(国语)」这类后缀。宁可漏合
    （「庆余年」与「庆余年 第二季」算两条），也不要把不同季的进度串到一起。
  - listHistory() 返回 HistoryGroup[]，形如
    { key, name, pic, items[], updatedAt }：items 按 updatedAt 倒序，
    items[0] 就是主记录；组间也按最近看过排。
    注意 IPC 的 history 现在返回的是**分组**，取值要写 history[0].items[0]。
  - 主记录 = **最近看过的那一条**（答复：行为最好猜）。
  - 其它源**保留成可切换的备选**（答复）：行上出现「N 个源」+ 几个小号 chip，
    点一下就把这一行换成那个源的集数与进度，「继续观看」跟着跳过去。
    手动选择存在 Library.tsx 的 pick: Record<groupKey, itemKey> 里。
  - 删除按钮删的是**这部片在所有源上的记录**（removeHistoryGroup(key)，
    key 就是归一化片名），有多个源时先 window.confirm 一次。
    IPC 通道从 library:remove-history 改名 library:remove-history-group。
  - 实测：素博的「斗破苍穹 年番」(42877) 与电影天堂的「斗破苍穹年番」(8164)
    合成一条，key 是「斗破苍穹年番」，items 两条，主记录是最近看的那个。

  顺带修掉一个模板式站点的真 bug：buildCmsUrl() 的模板分支**只替换不追加**，
  所以 `?ac={ac}&t={t}&pg={pg}&wd={wd}` 这种没有 {ids} 槽位的地址，详情请求
  永远带不上 ids，点进去一直解析不出剧集。现在模板替换完之后，如果
  query.ids 有值且结果里没有 ids= 参数就补上。
  （这个是自检先发现的：同名的第二个源一直没进历史。）

  自检的副作用也修了：[9] 段要把收藏与历史清干净才对得上数目，以前直接
  clearFavorites() + clearHistory()，等于**每跑一次自检就把使用者真实的
  收藏和观看记录抹掉**。现在先 library.get() 备份、全部跑完（放在最后，
  因为 [10] 段也会开播放页写一条）再按从旧到新重新写入。内容和排序都保住，
  但 updatedAt 会被刷新，所以还原后这些记录都显示「刚刚」。
  同时把 goto() 改成每次循环都重设一次 hash —— 渲染进程忙的时候偶尔会漏掉
  第一次导航，表现成「上一个页面还留在屏幕上」的假失败；hash 没变时不会
  触发 hashchange，重复设置是安全的。等待窗口也从 5s 放宽到 8s。

10. 已确认的产品决策
================================================================================

  原本的 Q1-Q6 已经问过了，结论记在这里，后面按这个走：

  Q1  是否内置公开订阅源    → 内置。**打包版首启自动装好并同步一次**，装完即用；
                              开发模式下只列在首启页/设置页，用户点一下才启用。
                              （原结论是「默认关闭，不做成默认启用」，理由是合规风险 +
                              源失效太快；后来用户要「带源的一键可用版本」，改成自动装，
                              但仍尊重删除：靠 data/bundled-sources.json 标志位记住装过，
                              用户自己删光之后重启不会再长回来。）
  Q2  外部播放器优先级      → 用户本机用 PotPlayer，探测顺序里排第一，
                              其后是 mpv、VLC。
  Q3  下载功能（M13）       → 暂不做，等主体功能稳定后再议。
  Q4  深色主题              → 先只做纯白。css 变量层已预留，以后加不用改组件。
  Q5  软件正式名称          → 就叫 TVBox Desktop。
  Q6  何时打包 exe          → 先不打包，等 M3/M4 做完再一起打。

  M2 期间追加的决策：
  · 播放器只做外壳，不内置解码器；浏览器放不了的格式交给本机 PotPlayer。
  · 外部播放器参数模板默认 {url}，可在设置里改。

  真实源验证后追加的决策：
  · Q1 落地形态：不引用仓库里的 samples/，点「添加」时把内置订阅的配置内容
    写到 <数据目录>/presets/<id>.json，保证仓库删了、换机器也能用。
  · 默认线路不能盲选第 0 条。实测量子资源把网页分享页放在 liangzi 线路、
    真正的 m3u8 放在 lzm3u8 线路，盲选会黑屏。现在用 pickPlayableLine()
    优先选「首集地址看起来是直链」的线路，播放页再给一个换线路的入口。
  · 判断线路时只看扩展名（m3u8/mp4/flv/...），不做 HEAD 探测——
    几十条线路逐个探测太慢，而且很多站点会拦 HEAD。

  用户反馈后追加的决策（合并 + 过滤解说）：
  · 换源不再用「详情页里的其它来源」chips，改成详情页的独立「选择片源」区块：
    列出这部片子在每个站点上的条目，当前这条标「正在看」，点「切换」换源并
    重新加载选集。片名与当前不同的显示「该源片名：…」，这是分辨同名不同版本
    的唯一线索。
  · 合并 key 用归一化片名：全角转半角 → 去掉尾部别名括号 → 去噪声词 → 去标点
    → 转小写。季数、部数、副标题一律保留（庆余年第一季 / 第二季 / 之帝王业
    必须分开）。尾部别名括号里若含「第N季/部/集/篇、特别篇、番外」等分季标记
    则不去掉，否则会把第一季和第二季合并。
  · 同一站点对同一部剧可能返回多条，合并前每站只留一条：按「有海报 > 有备注
    > 有评分，同分取名字短的」排序取第一条。这样卡片不会顶着
    「庆余年第二季粤语」这种后缀。
  · 过载合并比漏合并更安全：因为详情页能选片源，合多了用户还能换回来；
    所以宁可多合并一些写法变体。
  · 解说过滤默认开启（settings.filterCommentary = true），命中的片名关键词是
    解说 / 速看 / 盘点 / 混剪 / 拆解 / 影评 / 剧情介绍 / 一口气看完 / 分钟看完。
    搜索页和设置页都能关。只按片名判断，不做时长判断（列表接口通常不给时长）。

  用户要求加 AI 总结后追加的决策：
  · Key 由用户自己在设置页填，不内置、不代管；只存本机 data/settings.json，
    只在主进程里用。
  · 总结依据只用站点已有的字段（片名/类型/年份/地区/导演/演员/评分/备注/简介），
    站点没有分集剧情就如实说明，**不做二次抓取**（没有稳定来源，抓回来也不准）。
  · 默认 deepseek-flash + 关掉思考模式：剧情总结要的是快和便宜，不是推理链。

       /share/easy 这种 DPlayer 壳里能直接读出 m3u8 且标成「直接从播放页里取」；
       /share/hard 这种什么都读不出来的必须靠接口兜底、用的是那个可用的接口，

       失败、失败原因写清楚了、失败一次会记进战绩；战绩分开记（成功过的那条记
       ok 且 fail=0，失败过的那条记 fail 且 ok=0，不互相污染）；跑完只删自己
       加的两条、不留任何自检用的解析接口（对比跑之前的列表）
       （注意：**不**用 parse.list() 的顺序断言排行 —— 它给的是插入顺序，
        真正的排行发生在 resolve 时的 orderParses()，所以用实际解析结果来验）

       （按 key / 按中文名 + typeId=6 / 一个不存在的源）。条数断言里的标题就是
       那三条，所以命名空间一旦读错（退化成默认的「XX资源 · 最近更新」）这条
       和 origin 那条会一起红。断言配置里写几条就是几条、origin 全是
       config（没偷偷走默认那条路）、按 key 找得到源且拉到内容、按中文名也
       找得到源、指定了分类就按分类拉（桩上 t=6 回的是「自检分类片6第1页之N」，
       正则卡死这一点，防止拿最近更新糊弄过去）、写错的源只让那一行报错。
       界面侧再断言首页画成两条 .home-row（第三条只有错误文字）、卡片渲染出来
       了、第一条有片名
  [13] 外部播放器：**每台机器上的结果都不一样**（谁装了什么播放器就有什么），
       所以只断言形状与兜底 —— 检测返回的是数组、每一条都有名字和路径、都是
       .exe；player.open('javascript:alert(1)') 会被协议校验挡下（校验发生在
       找播放器之前，所以不会真的弹出播放器窗口）；设置页有「检测本机播放器」
       按钮；点完会给出「找到 N 个」或「一个都没找到」而不是一直转圈

  等待界面就绪一律用 waitFor 轮询（最多 12s），不用固定 sleep —— 搜索结果是
  一条条推过来的、详情要等主进程解析，死等固定毫秒数会在机器慢时假失败。
  切路由用的 goto() 每次循环都重设一次 location.hash：渲染进程忙的时候偶尔
  会漏掉第一次导航，表现成「上一个页面还留在屏幕上」的假失败；hash 没变时
  不会触发 hashchange，所以重复设置是安全的。等标题的窗口从 5s 放宽到 8s
  （「#/search → 分类浏览」这类标题是异步切过去的，5s 偶尔不够）。

  [9] 段的副作用：它要 clearFavorites + clearHistory 才能用固定数字断言，
  但这两句等于**每跑一次自检就把使用者真实的收藏和观看记录抹掉**。现在
  脚本**开头**（还没跑任何一段）先 library.get() 备份，**末尾**（放在 [10]
  之后，因为 [10] 也会开播放页写一条）再 clear + 按从旧到新重新写入。
  内容和排序都保住，但 updatedAt 会被刷新，所以还原后都显示「刚刚」。
  末尾会打印「已还原你原本的收藏与观看记录：N 部收藏 / M 条历史」，条数
  对不上时会额外警告一行。

  自检开头先 Page.reload 一次：编辑代码中途保存可能给 Vite 留下一次失败的
  HMR 报错，它会一直挂在页面 console 里，被「没有 JS 异常」断言误当成新错误。
  滚动自动加载这类依赖渲染帧的断言还要求页面可见 + 聚焦
  （Page.bringToFront + Emulation.setFocusEmulationEnabled），否则 Chromium
  会把 rAF 与 IntersectionObserver 完全节流，测出来永远是「没反应」。

  [2] 换完配置源之后还要再 Page.reload 一次 —— 这一步是必须的。自检是直接
  调 window.api.sources.* 换的源，绕过了渲染进程 store，不刷新的话渲染进程
  里还留着上一套 categories / live，后面的界面断言就会拿旧数据去比。表现
  成「自检第一次跑必挂、第二次才过」：第一次跑时应用配的是真实源（[1] 阶段
  把真数据缓存进了渲染进程），第二次跑时配置已经是上一轮留下的桩源，反而
  对得上 —— 这种假失败最容易被当成「环境问题」放过去。

  自检用的是本地桩，所以每一条断言的结果都是可判定的，不需要依赖外网。
  桩在搜索时会额外返回两条解说条目，专门用来验证解说过滤：
  一条片名里带「[电影解说]」，另一条片名刻意干净、只有分类是「影视解说」。
  连通性探测（关键词「测试」）不带它们，免得打乱「正常，返回 2 条」的断言。
  网页规则站的桩列表页不放解说条目——那条路本来就拿不到分类字段，
  放了等于在测一个现实中不存在的场景。

  桩的分类树照抄了真实站点里的几个坑：两层结构，而且父分类 id 在桩上同样
  查不出东西；「记录片」挂在电影片下面且用的是「记录」；「伦理片」也是
  电影片的子分类；「短剧」挂在连续剧下面；「动画片」挂在动漫片下面；
  「电影解说」是顶层。这样「必须展开成叶子」「沿祖先链归并」「沿祖先链挡掉」
  这几条才真的被断言到。
  桩每页只给 2 条，一屏装不满，所以自动加载会紧接着把第 2 页也拉过来
  （pageCalls 变成 [1,1,2,2]），断言只检查头两次是第 1 页。
  桩把每次收到的 pg 与 t 记在 state.pageCalls / state.typeCalls 里。
